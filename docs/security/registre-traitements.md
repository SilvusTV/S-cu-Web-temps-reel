# Registre des traitements — projet de démonstration
Date : 2026-10-06. Responsable du projet pédagogique : étudiant propriétaire du dépôt. Données exclusivement fictives, pas de collecte sur un salarié ou client réel. Les bases ci-dessous sont des hypothèses documentées pour la finalité métier, à valider avant tout usage réel ; elles ne prétendent pas autoriser la géolocalisation de personnes.
| Traitement / finalité | Personnes et catégories de données | Base légale envisagée pour service réel | Conservation réellement codée | Destinataires |
|---|---|---|---|---|
| Authentifier et limiter les accès | Clients, livreurs, dispatcher : identifiant, rôle côté serveur, JWT sub/exp/jti ; mot de passe de démo local | Exécution du contrat pour accès nécessaire au service, à confirmer pour chaque rôle | JWT/cookie 15 min ; comparaison KDF en mémoire ; .env conservé jusqu'à suppression/rotation volontaire, pas en git | Serveur ; navigateur détenteur du cookie HttpOnly |
| Informer le client de sa livraison | Commande, nom fictif, destination, statut, dernière position/ETA du livreur | Contrat pour la commande ; intérêt légitime à évaluer séparément pour les GPS du livreur | Dernière position en mémoire jusqu'au redémarrage ; Redis TTL 1 h d'inactivité ; buffer SSE 100 états/room pendant la vie du process | Client de cette commande, son livreur, dispatcher autorisé ; Redis interne |
| Superviser les zones et la présence | Identifiants actifs, zone GPS, socket id éphémère | Intérêt légitime soumis à nécessité/proportionnalité, information et mise en balance | Présence : lease 15 s renouvelé, grâce 5 s, nettoyage périodique ; clés Redis de présence TTL 30 s après dernier renouvellement | Membres autorisés de la même room et dispatcher |
| Valider le code et sa sécurité | Métadonnées de commits des contributeurs, résultats de tests, traces/captures avec comptes fictifs, SARIF et SBOM | Intérêt légitime de sécurité du service à justifier | Artefacts GitHub 7 jours ; historique source conservé pendant la vie du dépôt ; captures choisies dans docs jusqu'à suppression manuelle | Étudiant, enseignants/reviewers ; public si dépôt public ; GitHub |
La mémoire conserve uniquement les données fictives de seed ; elle ne fournit pas une purge métier par fin de livraison. Pas de logs d'accès ni de GPS persistants configurés (logger Fastify désactivé). Les signaux RTC sont relayés sans historique ; le data channel est éphémère, et les candidats ICE révèlent des informations réseau aux pairs. Aucune télémétrie externe applicative ni STUN tiers configuré par défaut.
Les stores sans volume de persistance perdent l'état au redémarrage global ; cela n'efface pas les sources et captures fictives du dépôt. À l'arrêt du projet : supprimer .env, conteneurs et captures devenues inutiles. Ne pas stocker de données réelles dans ces preuves publiques.
## Conditions avant usage réel
Définir l'entité responsable, l'information des personnes, les destinataires/hébergeurs, les durées métier et la procédure d'accès/effacement. Le suivi de livreurs doit être justifié et limité au temps et au besoin du service ; aucun consentement implicite ni simple compte technique n'autorise le suivi continu. Évaluer les obligations DPO/AIPD et les transferts selon le contexte réel.
